# crosvm xHCI: a Stop Endpoint on a STREAM endpoint reports ONE Stopped event, not one per stream ring

Repo: /root/gitrs/DroidVM/DroidVM_wip_usb/crosvm_build/external/crosvm, branch wip/usb, HEAD e5eece2 (Stop Endpoint fix = dc1e0bf + 9293b36 + 13242f9 + e5eece2; designs DESIGN-STOPPED.md and DESIGN-STOPPED-ISO.md in this directory).

## What the device run found (scratchpad/m6b/uas/run4, Windows pseudo-unprotected, UNITEK UAS enclosure 152d:a583, bulk streams)
- First (cold) attach of the disk, ETW: at the first Stop Endpoint on the UAS data-in stream endpoint (slot 1 DCI 7) TWO streams had a TD in flight (streams 2 and 3, as in run1 cycle 2). crosvm emitted a Stopped transfer event for EACH stream ring (design decision in DESIGN-STOPPED.md: "one Stopped event per stream ring that had a TD in flight"). Windows USBXHCI logged event 30 "Received duplicate Stopped Transfer Events" (HWVerifierFlag=0x2000000) in the same millisecond, and the stream-3 URB was then stranded for 16.28 s (disk.sys start 18.77 s) until UASPStor's request timeout aborted it. The nine later attach/detach cycles (only one stream in flight at the stop) were 0-1 ms and clean. Evidence: run4/w3WU.txt, w3WU-gaps.txt, w3WU-etw.txt, w4-windows-crosvm.log; run1's ETW for the pre-fix behaviour (4W2-etw.txt, one 4 s watchdog per Stop command even with two streams in flight).
- Spec (xHCI 1.2 4.12.1.1 / 4.6.9): an endpoint with streams has ONE current stream; Stop Endpoint stops the endpoint, the TD in progress is the current stream's TD, and the xHC generates ONE Stopped/Stopped-Length-Invalid Transfer Event (for that TD) and writes that stream's context (Stopped EDTLA); the other streams' TDs are simply pending on their rings and are not reported. USBXHCI keeps one watchdog per Stop Endpoint command and expects exactly one Stopped event.

## Decision (Fable 5.1, 2026-09-06)
- On a stream endpoint, a Stop Endpoint generates exactly ONE Stopped (26) / Stopped-Length-Invalid (27) Transfer Event across all its stream rings: the first stream ring to finish its stop with a cancelled TD claims it (crosvm runs streams concurrently, so "the current stream" is not knowable; any in-flight TD is a valid "TD in progress"). Every other stream ring that had a cancelled TD still REWINDS silently to that TD (so a later doorbell or Set TR Dequeue behaves as on hardware) and gets its Stream Context TR Dequeue Pointer/DCS written back, but NO event and NO Stopped EDTLA update (EDTLA only for the stream that emitted). A stream TD that completed before the cancel keeps its normal completion event (dc1e0bf) -- unchanged.
- Non-stream endpoints (bulk/interrupt/control/isoch, one ring) unchanged: one event per stop as today (e5eece2).
- The Stop Endpoint Command Completion is still sent after all rings parked (existing RingBufferStopCallback), so the single Stopped event precedes it.
- Implementation hint: DeviceSlot::stop_endpoint's stream branch creates one shared claim (e.g. Arc<AtomicBool> "stopped_event_claimed") per Stop command and hands it to each stream ring's stop (a RingBufferController::stop variant or a handler hook such as TransferDescriptorHandler::set_stop_event_claim(Option<Arc<AtomicBool>>) called before stop); the ring's finish_stop_and_park emits only if it wins the claim (compare_exchange), rewinds regardless, and reports back whether it emitted so the stream write-back sets Stopped EDTLA only for that stream. HCRST/halt/Reset Endpoint paths untouched. Keep e5eece2's drained-ahead gate as is (streams are bulk-only, never dequeue_all).
- Tests: a stream endpoint fixture (device_slot.rs test Fixture has stream endpoints; ring_buffer_controller / transfer_ring_controller tests have TrackedHandler-style handlers): two stream rings each with a cancelled TD -> exactly ONE Stopped event, both rings rewound, only the emitting stream's context gets Stopped EDTLA; one ring with a completed-before-cancel TD + one with a cancelled TD -> one Success event + one Stopped; a plain endpoint stop -> unchanged (existing tests stay green).
