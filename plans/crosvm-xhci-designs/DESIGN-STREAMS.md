# crosvm xHCI: USB 3.0 bulk streams (UAS) -- root cause, design, decisions

Repo: /root/gitrs/DroidVM/DroidVM_wip_usb/crosvm_build/external/crosvm, branch wip/usb, HEAD 11c5462.
xHCI model: devices/src/usb/xhci/*.rs; usbfs backend: devices/src/usb/backend/device.rs, usb_util/src/device.rs.
Symptom log: scratchpad/m6b/perf/run/5-windows-crosvm.log line 76:
  ERROR devices::utils::event_loop] removing event handler due to error: command ring TRB failed: failed to config endpoint: bad stream context type: 0

## (a) Root cause (analysis agent, verified against the code)

1. `create_stream_trcs` (device_slot.rs:879-885) walks all `2^(MaxPStreams+1)-1` primary Stream Context entries at Configure Endpoint time and returns `Err(BadStreamContextType)` on any entry whose SCT != 1.
2. Windows' USBXHCI populates only the streams UASPStor opened (URB_FUNCTION_OPEN_STATIC_STREAMS); the rest of the power-of-two array stays SCT=0 = "Not Valid" (xHCI 1.2 Table 6-13), which is exactly what the spec reserves for unused entries. Linux leaves them zero too (xhci-mem.c xhci_alloc_stream_info: "Leave the other unused stream ring pointers ... initialized to zero. This will cause the xHC to give us an error if the device asks for a stream ID we don't have setup"); it only survives crosvm because uas asks for 256, xhci clamps to HCC_MAX_PSA=16 entries, so num_streams == num_stream_ctxs and entries 1..15 are all SCT=1.
3. The Err propagates configure_endpoint (command_ring_controller.rs:210-212) -> .context("command ring TRB failed") (:433) -> handle_transfer_descriptor(..)? (ring_buffer_controller.rs:319-321) -> event_loop.rs:126-128 deregisters the command ring's fd. No Command Completion Event is ever sent and the completion Event is never signalled.
4. Nothing re-adds it: Xhci::reset() (mod.rs:467-474) only stops slots; the CommandRingController Arc lives on but its fd is gone. Hence the log's 10 s loop from line 77: Windows times out the command, HCRSTs, writes CRCR ("Write to crcr while command ring is running" because CRR never clears), repeat.
5. Spec: 4.6.6 Configure Endpoint validates Input Context *fields* (MaxPStreams <= MaxPSASize, EP Type, LSA) with Parameter Error; it never walks the Stream Context Array. Per 4.12.1.1 the xHC reads a Stream Context's TR Dequeue Pointer only when that stream becomes the endpoint's Current Stream (Idle -> Move Data, on doorbell/ERDY) and writes it back on Move Data -> Idle, Stop Endpoint (4.6.9) and halt; a Not Valid entry is an error *at use* (Transfer Event, Invalid Stream ID Error 34 / Invalid Stream Type Error 10), never at configure.

Write-back today: non-stream Stop Endpoint does write EP ctx TR Dequeue Ptr + DCS (device_slot.rs:705-708), halt too (:1077-1079). The stream branches (:722-729, :794-801, :1088-1094) assume trcs[i] <-> stream i+1 and always read/write a full 16-entry StreamContextArray (xhci_abi.rs:877-879).

## (b) Design (numbered; the implementer follows this)

1. transfer_ring_controller.rs:27-30: `TransferRingControllers::Stream(Vec<Option<Arc<TransferRingController>>>)`, index = stream_id-1, len = 2^(MaxPStreams+1)-1. `None` = Not Valid stream. Add the stream id to the ring name (:93, `slot_{} ep_{} stream_{}`) for the trace/debug log.
2. device_slot.rs `create_stream_trcs`: read the `pstreams` StreamContexts individually (read_obj_from_addr(addr + 16*i)), never a 16-entry array, so a MaxPStreams=1 (64-byte) array at a page end is not over-read. SCT=0 -> None; SCT=1 -> TRC seeded with pointer/DCS as now; SCT 2..7 with LSA=1 -> warn! + None (reserved; use-time error, not configure-time). Never Err on guest-supplied SCT.
3. device_slot.rs `add_one_endpoint` returns Result<TrbCompletionCode>; Err only for host faults (CreateTransferController, GetPort, guest-memory *write* faults). Guest-caused -> code + warn!: !valid_max_pstreams -> ParameterError(17); MaxPStreams>0 on a non-bulk EP type -> ParameterError; LSA=0 -> ParameterError (secondary arrays unsupported); EP Type 0 -> ParameterError; SCA/Input Context read fault -> ParameterError; alloc_streams failure -> ResourceError(7) (usbfs returns EINVAL on re-alloc without free, ENODEV on unplug). Add ParameterError=17, ResourceError=7, BandwidthError=8, InvalidStreamTypeError=10, InvalidStreamIdError=34, EndpointNotEnabledError=12, Stopped=26 to TrbCompletionCode (xhci_abi.rs:68-77) -- only the ones actually used need to exist, but adding the set is fine.
4. `configure_endpoint`: check slot state Addressed/Configured first -> ContextStateError(19) (4.6.6). On a non-Success from add_one_endpoint, drop_one_endpoint the endpoints this command already added, leave slot state alone, return the code (4.6.6: a failed command leaves the Output Context unchanged). drop_one_endpoint: free_streams failure -> warn!, not Err (the device may simply be gone). Deconfigure (DC bit) path unchanged.
5. `set_tr_dequeue_ptr` (:823-851): when EP ctx MaxPStreams>0, write pointer/DCS/SCT into Stream Context `stream_id` (SCA base = EP ctx TR Dequeue Ptr) and *leave the EP ctx pointer alone* (4.6.10) -- today it overwrites the SCA pointer with a ring pointer, so the next Stop/halt reads "stream contexts" out of the ring and writes them back over TRBs. stream_id 0 / out of range -> TrbError(5); slot None and command SCT=1 -> create the TRC lazily (this is the spec's way to (re)initialise a stream); endpoint not Stopped/Error -> ContextStateError.
6. stop_endpoint / reset_endpoint / halt_endpoint stream branches: iterate Some slots only, per-entry read-modify-write of that Stream Context (preserve Stopped EDTLA/reserved dwords); reset_endpoint requires Halted -> ContextStateError as it already does for the EP case (:760-767).
7. ring_doorbell / get_trc: stream slot None or id > len -> warn! and return Ok(false); stream_id != 0 on a MaxPStreams=0 endpoint -> ignore with warn (4.12.2).
8. Host streams must never leak: DeviceSlot::reset (HCRST / Reset Device) and Disable Slot currently clear trcs without free_streams (:856-863), so the next Configure Endpoint gets EINVAL from USBDEVFS_ALLOC_STREAMS (-> ResourceError after item 3 -> Windows retries forever; a guest warm reboot with the device still attached hits this). Free host streams for every Stream endpoint before dropping its trcs in reset()/disable slot; in add_one_endpoint, if that endpoint already holds Stream trcs, free first (warn) then alloc. free_streams on a gone device: warn only.
9. Tests (existing style: GuestMemory::new(&[(GuestAddress(0), pagesize())]) + EventLoop::start as in ring_buffer_controller.rs:392-470). Factor the SCA walk into a pure `read_stream_contexts(&GuestMemory, GuestAddress, max_pstreams) -> Result<Vec<Option<(GuestAddress /*dequeue*/, bool /*dcs*/)>>, TrbCompletionCode>` and test it in device_slot.rs: stream_array_with_not_valid_entries_is_accepted (16 entries, 1..8 SCT=1, rest 0 -> 15 slots, 8 Some); small_stream_array_at_page_end_is_not_over_read (MaxPStreams=1, array at pagesize-64); reserved_sct_is_not_valid_not_error; bad_max_pstreams_maps_to_parameter_error (5 > 3). Add check_struct_sizes for StreamContext == 16 in xhci_abi.rs tests (:900). If a DeviceSlot fixture is feasible (init_xhci_mmio_space_and_regs, Interrupter::new, UsbHub::new, a Register<u64> dcbaap), cover: configure_endpoint_with_not_valid_streams_returns_success_and_signals_event; set_tr_dequeue_on_stream_endpoint_keeps_sca_pointer; stop_endpoint_writes_back_only_populated_streams. In command_ring_controller a test that a handler returning an error completion code still signals complete_event (regression for the dead-handler symptom). Do not spend more than ~1/3 of the effort on the fixture; the pure-function tests are mandatory, the fixture tests are best effort (say which ones were written).

## (c) Follow-on gaps (for the verifier; ranked by the analysis agent)
1. Set TR Dequeue on a stream endpoint corrupting the SCA pointer -- fixed by item 5; evidence: ETW USBXHCI Endpoint_SetDequeuePointer with StreamId != 0, no ring corruption afterwards.
2. Stop Endpoint on a stream EP: Cancelled sends no Stopped(26) event and the written-back pointer is past the aborted TD; Windows re-points via Set TR Dequeue anyway. Watch for STATUS_CANCELLED URBs reappearing.
3. Re-alloc EINVAL after HCRST -- fixed by item 8; evidence: guest warm reboot with the device attached still gets the disk.
4. Stream count vs device companion descriptor MaxStreams (JMS583 likely 32 >= 15): low.
5. halt_endpoint halts all stream rings: recovers on the per-stream doorbells (start() clears halt_requested): low.
6. Transfer Event carries no Stream ID (correct per 6.4.2.1); short-packet residue on bulk-in stream URBs is the non-stream path: low.
Linux uas: no functional change expected (Linux fills every entry); item 5 also fixes a latent Linux bug on any UAS stall (xhci_cleanup_halted_endpoint issues Set TR Dequeue with a Stream ID).
