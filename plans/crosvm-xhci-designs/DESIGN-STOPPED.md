# crosvm xHCI: Stop Endpoint must report the TD in progress (Stopped transfer event) and rewind the ring

Repo: /root/gitrs/DroidVM/DroidVM_wip_usb/crosvm_build/external/crosvm, branch wip/usb, HEAD 391518c.
Why: on Windows every Stop Endpoint costs a fixed watchdog wait (4.0 s on a stream endpoint, 2.0 s on bulk/interrupt/isoch) because USBXHCI waits for the Transfer Event the spec promises for the TD in progress (xHCI 1.2 4.6.9) and crosvm never sends one; a TD that had actually completed before the cancel is reported as nothing at all, so Windows re-queues it and UASPStor waits 12 s more for a command the device already answered. Evidence: ETW decodes in scratchpad/m6b/uas/run1 (4W2-etw.txt, usbtrace-w*.xml) and the audio/camera timelines in scratchpad/m6b/windows3..5. Analysis (fable agent, read-only, verified against code lines at HEAD 391518c) follows verbatim.

All evidence is in hand; no further lookups are needed. Report follows (all times are guest ETW clock; crosvm log timestamps run +0.93 s ahead of it).

## (a) Sequence reconstruction

**Endpoint identity (correction).** DCI 7 (EP3 IN) is the UAS **data-in** pipe, not the status pipe: every one of the 5149 transfers on DCI 5 is a 1024-byte Sense-IU read, every one of the 5147 on DCI 2 is a 32-byte Command IU, DCI 7 carries the 524288-byte reads and the 8/12/192/256-byte INQUIRY/READ CAPACITY/MODE SENSE data, DCI 8 (EP4 OUT) is data-out. Stream pipe handles: W1 `UCX 18 ... EndpointPipeHandle=0xFFFFE38E9DC678A0 StreamID=2 -> 0xFFFFE38E9E9F3660, StreamID=3 -> 0xFFFFE38E9E9F36A8` (data-in), `0xFFFFE38E9E4605F0 StreamID=2 -> 0xFFFFE38E9E12E940` (status).

**Trigger (all three cycles, identical).** During disk.sys start the device answers a data-in command with its Sense IU without sending data (CHECK CONDITION, an unsupported page). The class driver then cancels the still-pending data-in URB; that is exactly Linux `uas.c:339-345` (`case IU_ID_STATUS: ... /* cancel data transfers on error */`) ending in `usb_unlink_urb(data_in_urb)` at line 384, and UASPStor does the same. In xHCI terms the unlink is Stop Endpoint + Set TR Dequeue.

**Cycle 1 (W2, 4W2-etw / usbtrace-w.xml).** Tag 2 = 192-byte data-in, URB 0xFFFFE38E9E57CD60 on stream 2; tag 3 = 256-byte data-in, URB 0xFFFFE38E9E581DE0 on stream 3.

**What USBXHCI waited for.** Nothing arrives during the 4 s in any cycle and the length is constant (4.008 / 4.015 / 4.000 s), so it is a timer, not a wait on crosvm. The same timer is visible on every other endpoint type crosvm has been traced with, at 2.0 s: audio ISO DCI 6 `02:32:29.432 31 ...003C0601 / .433 33 / 02:32:31.440 31 ...400601 + ISOCH Stop 0xC0000120` (windows3/audio-timeline.txt, and again at 31.510->33.511, 39.816->41.825, 50.111->52.120); camera interrupt DCI 3 `08:55:22.685 -> 08:55:24.688` and camera ISO DCI 11 `08:58:56.333 -> 08:58:58.350` (windows5/camera-timeline.txt); audio DCI 7 `07:16:31.839 -> 07:16:33.855` (windows4/audio2-timeline.txt). USBXHCI knows which TDs it put on the ring; after a Stop Endpoint completion it waits for the Transfer Event the spec promises for the TD in progress, gives up after 2 s (4 s on a stream endpoint), completes the URB with STATUS_CANCELLED and re-points the ring itself. Spec basis: xHCI 1.2 4.6.9 -- the xHC "shall generate a Transfer Event with the Completion Code set to Stopped, Stopped - Length Invalid, or Stopped - Short Packet for the TD that was in progress" (none if the ring was idle), those Transfer Events precede the Stop Endpoint Command Completion Event, and the Endpoint/Stream Context TR Dequeue Pointer is written with the pointer to the TRB in progress (plus Stopped EDTLA in the Stream Context, 6.2.4.1); 6.4.2.1: for Stopped (26) the TRB Pointer is the TRB in progress with ED=0 and TRB Transfer Length = its residual, 27 when that length is unknown; 4.6.10: Set TR Dequeue is legal only in Stopped/Error state and is how software skips or re-points after a stop.

## (b) crosvm today (branch wip/usb, HEAD 391518c)

- `devices/src/usb/xhci/device_slot.rs:851-912` `stop_endpoint` (and `reset_endpoint` 915-984): reads `trc.get_dequeue_pointer()`/cycle **before** `trc.stop()` and writes them to the Endpoint Context (877-878) or, via `write_back_stream_context` (829-847), to the Stream Context (893-901). That pointer was advanced past the TD's last TRB when the TD was dequeued (`ring_buffer.rs:93-99`, `dequeue_pointer += 16` per TRB), so the context receives the **next** TD / enqueue pointer, never the stopped TRB; Stopped EDTLA is left alone. Endpoint state is set to Stopped synchronously (909).
- `ring_buffer_controller.rs:229-258` `stop`: `handler.stop()` -> `transfer_ring_controller.rs:69-77` -> `XhciTransferManager::cancel_all` -> `xhci_transfer.rs:96-110` `try_cancel`: state Cancelling, `cancel_callback` -> `TransferHandle::cancel` `usb_util/src/device.rs:747-782` USBDEVFS_DISCARDURB. This is done for **every** in-flight URB on **every** stream of the endpoint (real hardware pauses the endpoint and keeps the other streams' TDs; crosvm discards them). Ring goes Stopping, callback held.
- Reap: `backend/endpoint.rs:235-245` -> `backend/utils.rs:83-97` `update_transfer_state` (Cancelling -> Cancelled for **any** status) -> `on_transfer_complete(&Cancelled, 0)` `xhci_transfer.rs:358-364`: signals the ring only, **no Transfer Event**. A URB that finished before the DISCARDURB (usbfs EINVAL -> `TransferAlreadyCompleted`, commit 76ed342) is reaped with status 0 and its data in guest memory, but takes the same path: reported as cancelled, no event, data silently lost.
- `ring_buffer_controller.rs:283-297` `on_event`: Stopping -> Stopped, `stop_callback` cleared -> last `RingBufferStopCallback` clone dropped (`ring_buffer_stop_cb.rs:36-40`) -> `command_ring_controller.rs:294-307` sends the Stop Endpoint Command Completion. So the completion is correctly emitted only after the cancel has landed, but no Transfer Event ever precedes it, and the written-back pointer is past the TD. A later Set TR Dequeue (`device_slot.rs:1001-1041`, streams 1045-1136) moves the ring; a bare doorbell would resume past the stopped TD.
- Halt path (`halt_endpoint` 1480-1525) is different and fine: the failing TD already produced its StallError event (`xhci_transfer.rs:384-390, 431-445`) before the ring parks.

## (c) The 12 s gap and the 22 s disk start

In cycle 2 crosvm cancelled both stream URBs. The device had already delivered tag 3's 256 bytes **and** its Sense IU (`14:56:06.039 27 Stop 0xFFFFE38E9E581DE0 NtStatus=0x0` on DCI 5 stream 3; in UAS the Sense IU follows the data), so the stream-3 URB was reaped complete (or unlinked with the data already ACKed) and reported to the guest as nothing at all. Windows therefore had a TD with neither a completion nor a Stopped event; after its 4 s watchdog it treated it as never started and re-queued it on the re-pointed stream-3 ring (`14:56:10.055 USBXHCI 45 DCI 7 StreamId=3`). crosvm submitted a fresh bulk-IN URB for tag 3, but the device had finished tag 3 and would never send data for it: no USB activity for 12.04 s until UASPStor's request timer fired and it issued ABORT TASK (`14:56:22.093 41 DCI 2 BytesTotal=16`) with another Stop Endpoint, another 4.0 s watchdog, Set TR Dequeue on stream 3 and the URB cancelled at 26.094; the retry then completed within 1 ms. disk.sys `ElapsedTimeMs=22043` = 4.0 (cycle 2) + 12.0 (dead tag-3 wait) + 4.0 (cycle 3) + the ~2 s of ordinary start work that also exists in W2 (32-byte data-out on DCI 8 at 48.062, next command at 50.040). W2's 6003 ms = 4.0 + 2.0 because there tag 3 had completed before the stop (stream 3 "already stopped") and the next tag-3 TD was held by USBXHCI until after the Set TR Dequeue.

## (d) Fix design

1. **Report real completions that raced the cancel** -- `backend/utils.rs` `update_transfer_state`: `Cancelling` + any status other than `Cancelled` (-ENOENT) -> `Completed`, so the reap path takes its normal Success/ShortPacket branch with `actual_length`. A TD that finished before the stop then gets its ordinary event, exactly as on hardware, and is not part of the stopped set. This alone removes the 12 s wait.
2. **Stopped event for a cancelled TD** -- `xhci_transfer.rs` `on_transfer_complete`, `TransferStatus::Cancelled` arm: take `bytes_transferred` (backends `endpoint.rs:238-243`, `device.rs:517-521` must pass `t.actual_length()` instead of 0), walk `transfer_trbs` summing `transfer_length()`, find the first TRB whose cumulative length exceeds the bytes moved: send `send_transfer_event_trb(TrbCompletionCode::Stopped /*26*/, atrb.gpa, cumulative - bytes, false, slot, ep)`; if the TD has no data-bearing TRB (bare Event Data/No-op) send `StoppedLengthInvalid` (27, add to `xhci_abi.rs` enum) with length 0. Always ED=0 pointing at the transfer TRB (4.11.5.2). Record `(seq, first_trb_gpa, first_trb_cycle, bytes)` in `XhciTransferManager` (`stopped: Mutex<Option<StoppedTd>>`, keep the lowest `seq`, a counter assigned in `create_transfer`) instead of emitting immediately when the ring is `dequeue_all` -- see 4.
3. **Rewind the ring to the stopped TD** -- new `TransferDescriptorHandler::finish_stop(&self) -> Option<(GuestAddress, bool)>` (default None). `TransferRingTrbHandler` returns the earliest stopped TD's first TRB and that TRB's own cycle bit (which equals the consumer cycle state at that point) and emits its Stopped event there (for `dequeue_all` rings this is where the single event goes, so several in-flight isochronous TDs produce one Stopped for the TD in progress and the later ones simply remain on the ring, as on hardware). `RingBufferController::on_event` Stopping branch (`ring_buffer_controller.rs:283-297`): call `finish_stop` **before** `*state = Stopped; stop_callback.clear()`, apply the rewind with `set_dequeue_pointer/set_consumer_cycle_state`; this orders Transfer Event before Command Completion (4.6.9) because the completion is the callback drop. The synchronous idle path in `stop()` and the `halt_requested` path stay as they are (no TD in progress / already reported).
4. **Write the context back when the ring has actually stopped** -- `device_slot.rs` `stop_endpoint`/`reset_endpoint`: move the Endpoint Context pointer+DCS write (877-878) and the per-stream `write_back_stream_context` (893-901, 965-973) into the `RingBufferStopCallback` closure, capturing the `Arc<trc>`s, so they read the rewound pointer; for the stream that held the stopped TD also `set_stopped_edtla(bytes & 0xffffff)` (6.2.4.1) and leave every other entry as the guest left it. Keep `set_endpoint_state(Stopped)` synchronous. Streams with nothing in flight keep today's behaviour (pointer at the next TD, no event).
5. **Tests.** `ring_buffer_controller.rs` (TrackedHandler + `finish_stop` returning a preset rewind): `stop_with_a_transfer_in_flight_rewinds_to_it_and_reports_before_the_callback` (order vector must read `["stopped", "callback"]`; after `start()` TD 1 is delivered again), `stop_of_a_drained_ring_rewinds_to_the_earliest_unfinished_descriptor` (dequeue_all, TDs 1-3 handed off, 1 completed, 2 and 3 cancelled -> rewind to 2, exactly one `finish_stop`), `halt_does_not_rewind`. `xhci_transfer.rs` (new test mod using `device_slot::test_util::Fixture` for interrupter/port, plus a `transfer_events()` helper next to `command_completions()` at 1747): `cancelled_td_reports_stopped_at_the_trb_in_progress` (TRBs of 0x100/0x200/0x300 bytes; 0x150 moved -> pointer TRB 2, length 0xB0; 0 moved -> TRB 1, 0x100; TD ending in an Event Data TRB -> pointer is the data TRB, ED=0), `a_cancelled_td_without_data_trbs_is_stopped_length_invalid`. `backend/utils.rs`: `a_transfer_reaped_complete_after_its_cancel_is_completed`. `device_slot.rs` (Fixture `stopped_stream_endpoint()`): `stop_endpoint_writes_the_context_from_the_ring_the_callback_sees` (start a stream ring, let it park, `set_dequeue_pointer` to a marker, stop -> Stream Context carries the marker and the untouched Stopped EDTLA), keep `stop_endpoint_writes_back_only_populated_streams` green. There is no fake `XhciBackendDevice` in tree (only host and fido backends), so end-to-end "Stopped precedes Command Completion with a real URB" stays a device test: re-run W1-W3 and confirm Stop Endpoint -> Set TR Dequeue drops from 4.0 s to ~1 ms and `WatchdogTriggered` disappears.

Would Windows skip the wait: the wait ends on a timer with nothing else arriving in every cycle, and the identical timer fires on every crosvm endpoint type; the one thing the spec promises and crosvm never sends is the Stopped event. Linux stays correct: `xhci-ring.c:2237-2245` keeps a TD on a Stopped event ("A stopped TD may be restarted"), `2921-2923` tolerates a Stopped event for a TD it already gave back, and `xhci_invalidate_cancelled_tds` (1066-1076) compares the written-back pointer with `trb_in_td`: with the pointer now inside the cancelled TD it takes the Set TR Dequeue path (`xhci_move_dequeue_past_td`) instead of `td_to_noop`, which is the path crosvm's streams commits already test.

## (e) Risks

- Behaviour change on the verified isochronous/interrupt paths: every audio/camera Stop Endpoint on Windows currently pays the same 2.0 s watchdog (quotes above), so those paths are the ones the fix alters most; re-run windows3/4/5 audio start/stop cycles, camera, and the Linux equivalents. With the earliest-only rule an isochronous stop yields one Stopped event per ring, which is what hardware gives.
- A stream endpoint yields one Stopped event per stream that had a URB in flight (crosvm runs streams concurrently, hardware has one active stream). USBXHCI tracks state per stream ring; Linux is tolerant; moderate risk, no evidence either way until run.
- Resuming by doorbell without Set TR Dequeue re-executes the stopped TD from its first unfinished TRB: bytes of a partially transferred bulk-IN TRB already in guest memory are re-read (hardware resumes mid-TRB). Windows and Linux always Set TR Dequeue past a cancelled TD; exposure is bounded to one TRB.
- Data ACKed by the host controller inside an unlinked URB is still lost (host-side, not fixable); it is now at least reported with a residual instead of vanishing.
- `finish_stop` runs on the event-loop thread under the ring `state` lock and takes the interrupter lock; nothing takes ring `state` while holding the interrupter (doorbell path takes `state` only), so no new lock order, but keep it that way.
- Reset Endpoint and halted rings must not rewind or emit Stopped (the StallError was already reported); the `halt_requested` path in `on_event` is untouched by the design.
