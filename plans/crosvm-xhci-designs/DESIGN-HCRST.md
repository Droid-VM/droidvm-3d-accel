# crosvm xHCI: HCRST must reset the command ring, CRCR and the interrupter

Repo: /root/gitrs/DroidVM/DroidVM_wip_usb/crosvm_build/external/crosvm, branch wip/usb, HEAD 11c5462 (the main checkout is BUSY with another agent -- work in a git worktree, see Rules).

## Symptom (phone 5568, app VM "Ubuntu-resolute", device attached by the daemon's auto-attach rule ~10 s after vm_start, i.e. BEFORE the guest firmware touched the xHCI; reproduced 3/3)
crosvm log (scratchpad/m6b/m4/run2/3F-crosvm.log lines 4532-4543, 3G-crosvm.log 4836-4844):
  13:48:57.595 usb_hub: backend attached to port 1 / port 1 changed before the guest set up its event ring; the change waits in PORTSC
  13:48:57.843 usb_hub: backend attached to port 2 / ... waits in PORTSC
  13:48:57.844 device_slot: xhci: stopping all device slots and resetting host hub        <- guest firmware (EDK2 XhciDxe) writes USBCMD.HCRST
  13:48:57.846 ERROR xhci: Write to crcr while command ring is running                    <- the firmware's CRCR write is REJECTED
  13:48:58.017 ERROR event_loop: removing event handler due to error: cannot dequeue transfer descriptor: cannot read guest memory: invalid guest address 0x0
Afterwards the command ring handler is gone; the kernel (23 s later) finds a dead controller: dmesg "Abort failed to stop command ring: -110 / xHCI host controller not responding, assume dead / HC died".
Audit facts: the "stopping all device slots" + "Write to crcr while command ring is running" pair fires ~270 ms after crosvm's "display backend android opened" on EVERY boot (13 historical hits, harmless when no port is connected because the firmware then issues no command). Only the address-0 dequeue is new: with a port connected at firmware time the firmware issues Enable Slot -> doorbell 0 -> the command ring controller runs with its initial dequeue pointer 0. A second rejected CRCR write ~5.5 s after the kernel's HCRST is the kernel's command-abort attempt (CRCR.CA, 5 s command timeout) -- consequence, not cause.

## Root cause (mod.rs)
- `Xhci::reset()` (mod.rs:467) only sets USBSTS.CNR, stops the slots' transfer rings and resets the hub; it never resets CRCR (CRR bit stays set -> `crcr_callback` mod.rs:313 rejects the guest's next CRCR write), never resets the command ring controller (dequeue pointer stays whatever it was, initially GuestAddress(0)), never resets the interrupter registers/state (IMAN/IMOD/ERSTSZ/ERSTBA/ERDP, event ring), DCBAAP or CONFIG. Only the USBCMD R/S=0 path (mod.rs:298) clears CRR.
- UNPROVEN: what sets CRR before the firmware's very first CRCR write. Candidates: the initial value of the crcr register (xhci_regs.rs:322-330 register! spec), a guest write storing bit 3 verbatim (crcr_callback returns `value` unmasked; CRR is read-only per spec), a doorbell-0 write before HCRST. FIND OUT by reading the code (register! spec, write masks, doorbell path) and explain it in the commit message. If the guest can set CRR by writing it, mask it.
- Spec (xHCI 1.2 4.2 / 5.4.1 USBCMD.HCRST / 5.4.5 CRCR / 5.5.2 interrupter registers): HCRST "resets the internal state machines and registers to their initial values": USBCMD=0 (R/S=0), USBSTS.HCH=1, CRCR=0 (CRR=0, pointer 0, RCS 0), DCBAAP=0, CONFIG=0, DNCTRL=0, IMAN=0, IMOD=default, ERSTSZ=0, ERSTBA=0, ERDP=0, all device slots disabled, ports reset. CNR=1 while the reset is in progress, then 0. CRCR bits 5:0 and 63:6: RCS/CS/CA are write-only (read 0); CRR (bit 3) is the only readable bit.
- The 11c5462 deferred-PORTSC path relies on the interrupter's event ring being "uninitialized" until the guest programs ERSTBA/ERSTSZ; after HCRST the interrupter still holds the firmware's old event ring, so a port-change event raised at the kernel's HCRST (hub.reset re-posts connect status) is written into the firmware's ERST memory, which the kernel now owns -> silent guest memory corruption hazard. Resetting the interrupter to the uninitialized state on HCRST closes it.

## Design
1. `Xhci::reset()`: build ONE `RingBufferStopCallback` whose closure runs after every ring is stopped: (a) reset all slots + hub (as today), (b) reset the command ring controller (dequeue pointer 0, consumer cycle state back to the initial value, state Stopped, no pending stop callbacks), (c) `regs.crcr.set_value(0)`, `dcbaap`/`config` to 0, (d) interrupter: `Interrupter::reset()` -> event ring back to the uninitialized/empty initial state, enabled=false, moderation timer disarmed (Timer::clear or equivalent) and armed flag false, pending interrupt state cleared; IMAN/IMOD/ERSTSZ/ERSTBA/ERDP registers set to their initial values (IMOD default 4000 = 1 ms per spec, whatever xhci_regs.rs uses at construction), (e) USBSTS: clear CNR (as today) and set HCH; keep the mfindex anchor reset. Pass the callback to BOTH `device_slots.stop_all(cb.clone())` and `command_ring_controller.stop(cb)` (RingBufferController::stop) so the command ring is quiesced before it is reset. Check `CommandRingTrbHandler`'s `stop()`/`is_quiesced()` semantics (transfer_ring_trb_handler / command_ring_controller.rs) so that a command ring that is Running-but-idle stops immediately (the same reasoning as ring_buffer_controller.rs:220-240) and one mid-command stops after it completes. Make sure `DeviceSlots::stop_all_and_reset` callers (if any other) keep working, or fold it into the new path.
2. `crcr_callback`: store only the guest-writeable bits (pointer 63:6 | RCS); never let a guest write set CRR; keep the existing rejection while CRR=1 (spec: writes ignored while running) but downgrade its log to warn! with the value. Optional, only if trivial and safe: CRCR reads return CRR only (spec) -- Linux's abort path polls CRR; do NOT break the CRR read.
3. Doorbell 0 (mod.rs:389-401) keeps setting CRR + start(); nothing else changes. When the command ring parks itself (ring empty -> Stopped in on_event), CRR stays set until R/S=0 or HCRST as today -- fine (spec: CRR clears when the ring stops on CS/CA/R/S=0/HCRST; parking on an empty ring is an implementation detail) -- but note it in a comment.
4. Lock/thread safety: `reset()` runs on the vcpu thread from the usbcmd write callback; the stop callback runs either synchronously there (all rings idle) or on the event-loop thread when the last in-flight ring stops. Every action in the callback must be safe from both (use the Arc handles; the interrupter is `Arc<Mutex<Interrupter>>` -- do not hold the interrupter lock while calling into rings; do not take the interrupter lock from a path that already holds it, e.g. inside an interrupter method).
5. Tests (host: `cargo +1.88.0 test -p devices --features usb usb::` with the rng shim, see Rules): (a) interrupter.rs: `reset_returns_event_ring_to_uninitialized` (after set_event_ring_seg_table_* + a sent event, reset -> send_port_status_change_trb fails with EventRingError::Uninitialized again / event_ring_is_empty semantics as appropriate, moderation timer not armed); (b) ring_buffer_controller.rs or command ring: stopping a Running-but-idle ring completes the callback immediately and a subsequent set_dequeue_pointer/start runs from the new pointer; (c) mod.rs-level if an Xhci fixture exists or is cheap: after `reset()`, crcr reads 0, a CRCR write is accepted (crcr value == written pointer|RCS), and HCH set. ## Addendum (Fable 5.1, verified in xhci_regs.rs:322-330)
The crcr register is constructed with `reset_value: 9` = RCS (bit 0) | CRR (bit 3) and `guest_writeable_mask: 0xFFFFFFFFFFFFFFC7` (bit 3 not guest-writeable, bits 4-5 reserved). So CRR is set from power-on: the guest's first CRCR write is rejected until something clears CRR (only USBCMD R/S=0 does). That is the "UNPROVEN" item above -- proven. Fix: reset_value 0 (spec 5.4.5 default 0) AND reset CRCR to 0 on HCRST (design item 1c). Keep the writeable mask (CRR not writeable). Mention the wrong reset value in the commit message.
