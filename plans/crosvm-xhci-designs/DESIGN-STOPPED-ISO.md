# crosvm xHCI: a drained-ahead (isochronous) ring must report ONE Stopped event, not one per cancelled TD

Repo: /root/gitrs/DroidVM/DroidVM_wip_usb/crosvm_build/external/crosvm, branch wip/usb, HEAD 13242f9 (dc1e0bf + 9293b36 + 13242f9 = the Stop Endpoint fix, see DESIGN-STOPPED.md in this directory).

## What the device run found (scratchpad/m6b/uas/run3, Linux protected guest, icSpring UVC camera, 3 x 60-frame captures = 6 stream stops)
- 119 guest kernel warnings `xhci_hcd ... Event dma <X> for ep 4 status 13 not part of TD at <Y> - <Y>` (ep_index 4 = DCI 5 = the UVC isochronous video-IN endpoint; status 13 = COMP_STOPPED). A/B on the previous binary b55fcee2 (391518c, same workload): ZERO. The warnings come in bursts, one burst per stream stop; every surplus event names a distinct TRB ahead of the single-TRB TD the driver expected (the ring is drained ahead: isochronous rings hand many TDs to the backend at once, RingBufferController::set_dequeue_all).
- Windows was verified only on the audio isoch OUT and the camera interrupt IN endpoints (gaps 4 s / 2 s -> 1 ms, PASS); the UVC isochronous video-IN stop path was NOT exercised on Windows, so it may be hit silently there too.
- Possible fps side effect: 3 of 6 Linux captures ran at ~15 fps vs 19-20 fps on the previous binary (not proven; re-measure A/B after the fix).

## Design decision (DESIGN-STOPPED.md already says this; the implementation did not honour it for dequeue_all rings)
- On a `dequeue_all` ring, when Stop Endpoint cancels several in-flight TDs, exactly ONE Transfer Event is generated: Stopped (26) / Stopped - Length Invalid (27) for the EARLIEST unfinished TD (lowest sequence), pointing at its first unfinished TRB, with the residual; the ring rewinds to that TD; every later cancelled TD produces NO event (they stay on the ring behind the rewind point, as on hardware where only one TD is "in progress"). A TD that really completed before the cancel keeps its normal completion event (dc1e0bf), which is fine.
- On a non-dequeue_all ring (bulk/interrupt/control, one TD in flight per ring; stream rings likewise) behaviour stays exactly as in 13242f9 (verified on Windows: 1 ms gaps).
- Implementation hint: in xhci_transfer.rs the Cancelled arm must not emit for a dequeue_all ring; instead XhciTransferManager::record_stopped keeps the earliest and TransferDescriptorHandler::finish_stop (called from RingBufferController's Stopping branch / synchronous-park branch) emits the single event and returns the rewind. Check how `dequeue_all` is known at the transfer level (the ring controller owns the flag; pass it into the manager/handler, or have the handler defer emission always and let finish_stop emit -- but then the non-dequeue_all ordering "Stopped before the Stop Endpoint Command Completion" must still hold; it does, since finish_stop runs before the stop callback is released).
- Halt / Reset Endpoint / HCRST paths unchanged. Linux: `xhci_handle_cmd_stop_ep` / `xhci_invalidate_cancelled_tds` tolerate a Stopped event for the TD in progress; they warn "not part of TD" for any other.
- Tests: ring_buffer_controller + transfer_ring_controller/xhci_transfer level: a drained ring with 3 cancelled TDs -> exactly ONE Stopped event (earliest), rewind to it; one TD completed-before-cancel + 2 cancelled -> completion event for the first, one Stopped for the earliest cancelled; a non-dequeue_all ring with 1 TD -> unchanged (existing tests stay green). ## Erratum (after implementation, 2026-09-06)
The "status 13 = COMP_STOPPED" label above is wrong: status 13 is COMP_SHORT_PACKET. The flood was not surplus Stopped events (13242f9 already emitted at most one per stop) but ordinary Short Packet completions: dc1e0bf's "a transfer that completed before its cancel keeps its completion" rule fired for the hundreds of one-packet isochronous URBs whose USBDEVFS_DISCARDURB lost the race (usbfs EINVAL, reaped with status 0). The fix (crosvm e5eece2) gates that rule off on drained-ahead rings: a Cancelling transfer reaped with any status except NoDevice joins the single-Stopped set. See USB_PASSTHROUGH_SURVEY.md §9.1.
