## Hypothesis (Fable 5.1) -- VERIFY IT FROM THE ETW BEFORE CODING
crosvm cancels EVERY stream ring's in-flight URB at Stop Endpoint (device_slot.rs stop_endpoint stream branch -> each ring's handler.stop() -> cancel_all), reports ONE Stopped event (f96fd65), and rewinds the other ("silent") rings to their cancelled TD. Real hardware stops only the current stream's TD; the other streams' TDs stay pending and are executed again as soon as the endpoint is restarted by ANY doorbell (the device ERDYs the pending stream). In crosvm each stream ring restarts only on a doorbell carrying ITS stream id (DeviceSlot::ring_doorbell -> get_trc(index, stream_id).start()). If Windows, after the stop, re-points (Set TR Dequeue) and rings the doorbell only for the stream it considers current (the reported one) and leaves the other stream's TD "pending on hardware", the silent ring never restarts -> its TD is never re-executed -> stranded until UASPStor's timeout. Warm cycles may differ because the class driver cancels both tags' URBs (Set TR Dequeue for both streams + doorbells for both).
Check in cold1/cold3 vs cold2: which stream was reported (Stopped event TRB pointer -> stream), which stream got Set TR Dequeue commands (stream id in the command TRB dword2 bits 31:16), whether any transfer (USBXHCI 41/45) happened on the stranded stream between the stop and the 16 s timeout, and whether there is any doorbell evidence. If the stranded stream is the silent one and got no re-point/no activity -> the hypothesis holds.

## Decision (if the hypothesis holds)
- A doorbell for a stream endpoint (any valid stream id) restarts EVERY populated stream ring of that endpoint that is Stopped (not halted), not only the addressed one: DeviceSlot::ring_doorbell for TransferRingControllers::Stream -> start() the addressed ring and every other Some ring (an empty ring parks again at once; a rewound ring re-executes its TD -- a fresh URB fetches the data the device is still holding for that tag). A doorbell with an invalid/Not Valid stream id stays ignored as today. Safe ordering: Windows/Linux issue all their Set TR Dequeue commands before ringing any doorbell, so every ring's pointer is already where software wants it when the first doorbell restarts them; a ring the guest halted is not restarted (halt_requested path untouched).
- Also: f96fd65 added an error!-level line "endpoint at index N is not running" when Stop Endpoint arrives on a non-Running endpoint (Linux does this legitimately; run5 Linux log shows it twice). Downgrade it to debug! (the Context State Error completion is the guest-visible answer).
- If the evidence points elsewhere (e.g. Windows DID re-point/doorbell the stranded stream and crosvm did not run it), design the right fix instead and explain -- but keep the change minimal and inside device_slot.rs / ring_buffer_controller.rs.
